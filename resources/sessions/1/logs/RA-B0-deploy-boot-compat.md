# RA-B0 Deploy-env boot compatibility (Option 3)

Status: DONE — branch `ts-migration/backend`. Realignment spinoff (see
[plans/02-frontend-backend-realignment-spinoff.md](../plans/02-frontend-backend-realignment-spinoff.md)).

Makes the rearchitected backend boot and serve under the `release_manager` deploy
stack (its concrete "app runs together" target) without editing `release_manager`,
so `docker compose up` works on localhost/VPS with no AWS. The operator sets key
material once (generated by a helper); everything else is backend-side.

## Problem (verified against release_manager/BOE_APP/docker-compose.yml)

The deploy backend env is the legacy contract: `ACCESS_TOKEN_SECRET`/
`REFRESH_TOKEN_SECRET`, `CORS_ORIGIN`, `DATABASE_URL`, `SEED_*`/`ADMIN_*`, and
`seed` runs `npm run seed:auth`. The rearchitected backend instead requires ES256
PEMs + HMAC/cursor/crypto keys + `WEB_ORIGIN_ALLOWLIST`, treated AWS SES/SNS as
mandatory, had no `seed:auth` script, and its Dockerfile never copied
`db/migrations`. Net: the backend crashed at boot, seed failed, and the DB stayed
empty.

## Changes

RA-B0a (commit `8f7ea14`):
- `runtime/environment.ts`: accept legacy `CORS_ORIGIN` as the origin allowlist
  source when `WEB_ORIGIN_ALLOWLIST` is unset; make `AWS_REGION`/`SNS_TOPIC_ARN`/
  `SES_CONFIGURATION_SET` optional (`emailConfigured` flag; `sesConfigurationSet`
  defaults to a non-empty placeholder); accept a `\n`-escaped PKCS#8 signing key.
- `runtime/composition.ts`: register the signed SNS ingress only when AWS is set.
- `runtime/health.ts`: email is an informational readiness check; the database is
  the hard gate (so a no-AWS deployment reports ready). Unit test updated.
- `Dockerfile`: `COPY db/migrations` into the runtime image.
- `test/integration/deployBoot.integration.test.ts`: boots under a deploy-shaped
  env (CORS_ORIGIN, no AWS, escaped key), serves health + consent docs, omits SNS.

RA-B0b (this commit):
- `src/scripts/seedAuth.ts` + `package.json` `seed:auth`/`seed:auth:dev`: real
  auth seed — catalog + an idempotent admin bootstrap (active `users`, Argon2id
  `user_credentials`, `superadmin` permission grants + role assignment) from
  `ADMIN_*`/`SEED_ADMIN_*`, guarded by `SEED_AUTH_ENABLED`/
  `SEED_AUTH_ALLOW_PRODUCTION`/`SEED_AUTH_OVERWRITE`.
- `scripts/generate-deploy-secrets.ts` + `keys:generate`: prints a ready-to-paste
  `.env` block of the key material the deploy env lacks (ES256 keypair, HMAC/
  cursor/crypto keys). Secrets are generated fresh and never committed.
- deployBoot test extended: `seed:auth` bootstraps an admin who logs in via
  `POST /v1/auth/web/login` (superadmin role + permissions), and re-running is
  idempotent.

## Operator steps (to boot the deploy stack)

1. `cd backend_controller && npm run keys:generate` — paste the block into your
   deploy env (`release_manager/BOE_APP/.env`); set `ACCESS_TOKEN_ISSUER`/
   `ACCESS_TOKEN_AUDIENCE` to real values. Leave AWS lines commented to run
   without email.
2. Ensure `CORS_ORIGIN` lists your landing + admin origins (already in the deploy
   env). No `WEB_ORIGIN_ALLOWLIST` needed.
3. Rebuild the backend image (now includes `db/migrations`) and `docker compose
   up`: `migrate` applies `009-018`, `seed` (`seed:auth`) seeds roles/permissions/
   consent + the admin login, `backend` boots and serves; `landing` proxies to it.

## Not included / notes

  (rotation on restart would break sessions) — the operator sets them once.
- Building the Docker images + a live `docker compose up` is the user's release
  pipeline (`release_manager/export.sh` + `deploy.sh`) and the APK/emulator build
  stays on the user's machine; the agent verified via the deploy-shaped boot test.
