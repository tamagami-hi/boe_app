;; ─────────────────────────────────────────────────────────────────────────────
;; WHAT THIS SETUP DOES
;;
;; Two mail systems share this domain and must not fight:
;;
;;   INBOUND  — Zoho. MX on the apex routes support@beonedge.in to the Zoho
;;              mailbox. Untouched by anything below.
;;   OUTBOUND — split. Zoho sends human replies typed in webmail; Amazon SES
;;              sends the application's automated mail (verification links,
;;              approval and rejection notices).
;;
;; Both sign with DKIM on this domain under different selectors, so both are
;; authenticated and neither invalidates the other.
;;
;; ─────────────────────────────────────────────────────────────────────────────
;; ONE DELIBERATE DEVIATION FROM THE AWS EXPORT — READ THIS
;;
;; dns-records.csv asks for:
;;
;;     TXT  _dmarc.beonedge.in  "v=DMARC1; p=none;"
;;
;; That record is NOT in this file, on purpose. It is AWS's generic starter
;; policy for domains that have no DMARC yet. This domain already has a
;; stricter, fully-formed one (p=quarantine with aggregate + forensic
;; reporting), and adding AWS's alongside it would be actively harmful:
;;
;;   - Only one DMARC record may exist at _dmarc. Per RFC 7489 §6.6.3, when
;;     policy discovery finds MORE THAN ONE record, DMARC is not applied to
;;     the message at all. Two records is worse than either one alone.
;;   - Replacing the existing record with AWS's would drop the policy from
;;     quarantine to none and lose the rua/ruf reporting addresses.
;;
;; The existing DMARC is already correct for SES. It sets adkim=r and aspf=r
;; (relaxed alignment), and:
;;   - SES Easy DKIM signs with d=beonedge.in            -> DKIM aligns
;;   - the custom MAIL FROM is a subdomain of beonedge.in -> SPF aligns
;; so SES mail passes DMARC under p=quarantine without any change here.
;;
;; ─────────────────────────────────────────────────────────────────────────────
;; WHY THE APEX SPF IS NOT TOUCHED
;;
;; The apex keeps "v=spf1 include:zoho.in ~all" with NO amazonses include.
;; That is correct and intentional. SES is configured with a custom MAIL FROM
;; domain (support.beonedge.in), so the envelope sender is on that subdomain and
;; SPF is evaluated against the subdomain's own SPF record further down. Adding
;; include:amazonses.com to the apex would be redundant and would spend one of
;; SPF's 10 DNS-lookup budget for nothing.
;;
;; ─────────────────────────────────────────────────────────────────────────────
;; CLOUDFLARE: THE NEW RECORDS MUST BE "DNS ONLY" (GREY CLOUD)
;;
;; Every existing CNAME here carries cf-proxied:true. The three DKIM CNAMEs
;; below MUST NOT be proxied. A proxied CNAME resolves to Cloudflare's IPs
;; instead of returning the amazonses.com target, so SES verification never
;; succeeds and signing silently fails. Set each to DNS only.
;;
;; MX and TXT records are never proxied, so those need no action.
;;
;; ─────────────────────────────────────────────────────────────────────────────
;; DO NOT IMPORT THIS FILE INTO CLOUDFLARE
;;
;; This is the intended END STATE, for review and for diffing against a future
;; export. It is not an import payload. Cloudflare's import is additive — it
;; creates records and does not overwrite existing ones — so importing this would
;; try to re-create all 14 records you already have. A second apex SPF TXT or a
;; second _dmarc TXT does not merge; it breaks SPF and DMARC outright.
;;
;; To apply the change, import the companion file instead, which contains only
;; the five new records:
;;
;;     release_manager/aws_ses/beonedge.in.ses-only.import.txt
;;
;; New records use TTL 300 so a typo can be corrected quickly during
;; verification. Raise them to 3600 once SES reports DKIM as verified.
;;
;; ─────────────────────────────────────────────────────────────────────────────
;; named-checkzone STATUS (verified 2026-08-08)
;;
;; This file does not load under named-checkzone, and that is expected:
;;
;;     beonedge.in: CNAME and other data
;;
;; The apex carries a CNAME (the Cloudflare tunnel) alongside MX and TXT, which
;; RFC 1034 forbids. It works only because Cloudflare flattens apex CNAMEs at
;; serve time — the record is legal in Cloudflare and illegal in BIND.
;;
;; It is inherited, not introduced. The untouched Cloudflare export
;; (beonedge.in.txt) produces the identical error. Removing just that one line
;; makes this file load cleanly:
;;
;;     grep -vE '^beonedge\.in\.[[:space:]]+1[[:space:]]+IN[[:space:]]+CNAME' \
;;       beonedge.in.with-ses.txt > /tmp/noapex.zone
;;     named-checkzone beonedge.in /tmp/noapex.zone      # -> OK
;;
;; So: a "CNAME and other data" error on the apex is the known baseline. Any
;; OTHER error means this file has drifted and should be fixed.
;;
;; The import payload (beonedge.in.ses-only.import.txt) validates OK outright,
;; once a synthetic SOA is prepended for the checker's benefit.

;; ── SES custom MAIL FROM: support.beonedge.in ────────────────────────────────
;; NOTE ON THE NAME: this subdomain exists only to carry the SMTP envelope
;; sender and to receive SES bounce notifications. It is a SEPARATE DNS
;; namespace from the support@beonedge.in mailbox — that address is routed by
;; the apex MX records above and is completely unaffected.
;;
;; "support" is a confusing choice for this role (mail./ses./bounce. are the
