# Design — PhonePe moves out of `boe_app` and behind a relay in `boe_landing`

Status: **for discussion.** Nothing implemented.

## What this does and does not achieve

**Does:** removes PhonePe credentials, SDK and env keys from `boe_app` entirely; consolidates the whole
PhonePe integration into one service on the approved domain; gives one integration point for both the
dev and production apps.

**Does not:** lift `INTERNAL_SECURITY_BLOCK_1`. Four inputs have been varied and none moved
`Transacting_URL` (Entries 028, 032, 033). The pay call is server-to-server with no `Origin` or
`Referer`, carries four fields, and both containers share one egress address, so PhonePe cannot tell
which of our processes called it. Sandbox credentials are still needed for dev testing, and PhonePe
approval is still needed for production. This design should be judged on its architectural merits, not
as a fix.

## One thing to be clear about up front

The payer's browser still goes to `mercury-t2.phonepe.com`. The relay changes **who creates the order**,
not **where the payer pays**. So:

- `CHECKOUT_ORIGIN_ALLOWLIST` in `frontend_stack_ts` stays, and still lists the mercury hosts.
- The client still receives a redirect URL and still navigates to PhonePe.
- "The UI does not change" holds, but it means the PhonePe page is still visible to the user.

There is no configuration in which payments happen without the payer reaching PhonePe.

## The boundary: what crosses it

The load-bearing decision. Two options, and they are not close.

### A. Relay is stateless; `boe_app` stays the system of record — recommended

`boe_app` keeps `investment_orders`, `payments`, `payment_attempts`, `investment_allocations`,
idempotency keys, the `version` optimistic-concurrency columns, reconciliation and the audit trail.
`boe_landing` holds credentials and speaks PhonePe. It stores nothing.

This still satisfies "no PhonePe code or env in `boe_app`", because the abstraction already exists:
`PaymentGateway` is a port with one implementation today. A second implementation that speaks to the
relay instead of PhonePe leaves the routes, the state machine and the idempotency logic untouched.

### B. Relay owns payment records

`boe_app` asks "collect ₹X for order Y" and later hears "paid" or "failed".

Consequences to accept before choosing this: money truth is split across two databases; the
webhook → allocation step stops being one transaction; refunds, statements, reconciliation and audit
must join across a service boundary; and the reconciliation worker needs a view it no longer owns. For
a fintech I would not choose this without a specific reason.

**Recommendation: A.** It gets everything asked for except splitting the ledger, which is the one part
that is genuinely dangerous to split.

## Contract sketch (option A)

Initiation, private:

```
POST /internal/v1/phonepe/checkout
  { merchantOrderId, amountPaise, expireAfterSeconds, redirectUrl }
  → { providerOrderId, checkoutUrl, expiresAt }

POST /internal/v1/phonepe/order-status   { merchantOrderId } → provider status facts
POST /internal/v1/phonepe/refund         { merchantRefundId, merchantOrderId, amountPaise }
POST /internal/v1/phonepe/refund-status  { merchantRefundId }
```

Callback, public on the approved host:

```
POST /api/v1/provider-events/phonepe/payment       (already proxied and verified)
POST /api/v1/provider-events/phonepe/subscription
```

`merchantOrderId` is generated by `boe_app` and passed through unchanged. The relay must never mint an
id of its own — PhonePe dedupes on `merchantOrderId`, so passing it through is what preserves the
existing idempotency and dispatch-claim guarantees (migration 043) across the new boundary. A relay
that generated ids would create a second PhonePe order on retry, which is a double charge.

## Six things that need deciding or designing carefully

**1. Callback verification belongs in `boe_app`, not the relay.** The relay should forward the raw body
and PhonePe's auth header verbatim, and add its own HMAC. Then PhonePe's signature is still checked by
the party that owns the payment record, and the relay is a dumb pipe. If the relay verified and then
asserted "this is genuine", `boe_app` would be trusting a second service on the most security-sensitive
step in the system.

**2. Callback durability without giving the relay state.** Today PhonePe retries against `boe_app`
directly. With a relay in between: forward synchronously, and if `boe_app` answers non-2xx, return
non-2xx to PhonePe so **PhonePe** retries. That preserves at-least-once delivery and keeps the relay
stateless. The alternative — the relay queues and retries — is state, and state is what option A is
avoiding.

**3. Authentication on the initiation leg.** Not an `Origin` check: the caller is a server and sends no
`Origin`. Shared Docker network so the endpoint is not publicly routed at all, plus HMAC over body +
timestamp + nonce so a captured request cannot be replayed. The two containers are on separate networks
today (`boe-landing_edge`, `boe_dev_frontend`) and need an explicit shared one.

**4. Reconciliation must move too.** The payments worker calls `getOrderStatus` on its own schedule. If
that keeps talking to PhonePe directly, PhonePe env keys stay in `boe_app` and the migration is partial.
This is the step most likely to be forgotten.

**5. AutoPay is a second integration, not a footnote.** `phonePeRecurringGateway`, mandates, the
collections worker and the subscription callbacks are a comparable surface to one-time payments.
`PHONEPE_AUTOPAY_ENABLED=false` today, so it can be deferred — but "remove all PhonePe code" is not true
until it moves, and leaving it behind means the env keys stay.

**6. Payments now depend on the landing site's availability and deploy cadence.** A marketing-site
deploy becomes a payments outage window. Either accept that, or give the relay the same health checks
and monitoring the backend has. Related: two repos means no lockstep deploy, so the relay contract needs
a version prefix and a rule — landing deploys first, `boe_app` second.

## What actually leaves `boe_app`

Removed: `providers/phonepe/*` (api client, checkout gateway, recurring gateway), every `PHONEPE_*` env
key, the checkout-origin allowlist in the backend.

Kept: the `PaymentGateway` port, `clientOrderRoutes`, the order and payment state machines,
`payment_attempts` and its dispatch claim, idempotency, reconciliation, allocations, audit, and
`CHECKOUT_ORIGIN_ALLOWLIST` in the frontend.

Added: a `relayPaymentGateway` implementing the same port, plus `PAYMENTS_RELAY_URL` and
`PAYMENTS_RELAY_SECRET`. `envPassthrough.test.ts` will fail if either is added to a stack
`.env.example` without a compose passthrough.

## Decisions needed from the maintainer

1. **Option A or B** — does `boe_app` remain the system of record for money? (Recommend A.)
2. **AutoPay in scope now, or one-time payments first?** (Recommend deferring; it doubles the surface.)
3. **Accept that payments depend on landing-site uptime**, or add matching monitoring first?
4. Understood and accepted that this does **not** lift the current block, and sandbox credentials are
   still the route to a working dev payment today?
